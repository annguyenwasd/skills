# /fix - Checklist-Gated Bug Fix

Fix a bug only after the user approves an observable acceptance checklist.

## Inputs

The user should describe:

- The bug or failing scenario
- Actual behaviour: what happens now
- Expected behaviour: what should happen instead

If actual or expected behaviour is missing or ambiguous, ask one focused question before creating the checklist.

## Workflow

1. Understand the bug.
2. Create the checklist file.
3. Show the checklist and wait for approval.
4. After approval, fix the bug.
5. Run `/verify --checklist <path>`.
6. If every item passes, report done. If any item fails, fix and verify again until pass or blocked.

Do not edit application code before the checklist is approved.

## Before checklist

Run one bounded discovery pass to understand the externally observable behaviour:

- Read the user's bug description.
- Read the relevant routes/pages/tests/modules needed to identify the public behaviour.
- Prefer existing tests and public interfaces over implementation guesses.
- Stop early once you can write concrete observable checklist items.

## Checklist export

Write an acceptance checklist before fixing.

**What to include:** each user-observable behaviour required for the bug to be fixed, written in acceptance-test form:
`Given [initial state/context], when [event/action], then [expected observable behaviour]`

Each item must be specific enough for `/verify` to check from outside the implementation. Include the page/path for UI flows, the exact control or action, and the exact visible text, API status, field, redirect, or state change expected.

Include behaviour a user, browser test, or HTTP API can observe: API responses, UI flows, component states, form validation, API errors shown in the UI, and persisted outcomes visible through later app/API reads.

Skip internal implementation details: database indexes, table structure, queues, private functions, component names, hooks, CSS class names, or pure visual styling unless it changes observable behaviour.

**Slug derivation:** kebab-case the bug topic from the input. If a path, issue number, or ticket title is supplied, use the most specific human-readable title. If unclear, ask once for a slug.

**Write to:** `<project-root>/.checklist/fix-<slug>/FIX.md`

If not in a git repo, write to `./.checklist/fix-<slug>/FIX.md`.

If the file already exists for this slug, ask once: overwrite, or pick a new slug.

**File format:**

```markdown
# Fix Checklist: <Bug Title>
<!-- Generated by /fix on <YYYY-MM-DD HH:MM:SS> -->

## Bug
- Actual: <what happens now>
- Expected: <what should happen instead>

## API
- [ ] Given <initial state/context>, when <event/action>, then <expected observable behaviour>

## UI
- [ ] Given <initial state/context>, when <event/action>, then <expected observable behaviour>

## Validation
- [ ] Given <initial state/context>, when <event/action>, then <expected observable behaviour>

## Flow
- [ ] Given <initial state/context>, when <event/action>, then <expected observable behaviour>
```

Omit empty categories.

After writing, ensure `.checklist/` is gitignored:

```bash
if ROOT="$(git rev-parse --show-toplevel 2>/dev/null)"; then
  grep -qxF '.checklist/' "$ROOT/.gitignore" 2>/dev/null || echo '.checklist/' >> "$ROOT/.gitignore"
fi
```

Then show the checklist path and contents to the user:

`Checklist -> .checklist/fix-<slug>/FIX.md`

Ask: `Approve this checklist so I can fix the bug?`

Stop until the user approves.

## Fix phase

After approval:

1. Write or update the smallest useful test that fails for the actual behaviour and passes for the expected behaviour.
2. Run the targeted test and confirm it fails for the right reason.
3. Make the minimal code change.
4. Run the targeted test again.
5. Run the relevant broader test suite.
6. Check lints for edited files.

Keep changes scoped to the approved checklist. If discovery shows the checklist is wrong or incomplete, stop and ask to update it before continuing.

## Verification phase

Run:

```bash
/verify --checklist .checklist/fix-<slug>/FIX.md
```

Use the actual checklist path.

If `/verify` reports only `PASS`, the bug is fixed.

If `/verify` reports `FAIL` or `TIMEOUT`, fix the cause and rerun `/verify` until all pass or you hit a real blocker.

If `/verify` reports `ASSUMED` or `UNVERIFIABLE`, explain the limitation and either tighten the checklist or ask the user whether the result is acceptable.

## Done criteria

The task is complete only when:

- The approved checklist exists at `.checklist/fix-<slug>/FIX.md`
- Application code changes are scoped to that checklist
- Relevant tests pass
- `/verify --checklist .checklist/fix-<slug>/FIX.md` passes every item, or any non-pass result is explicitly accepted by the user
